一、目前網站版生成流程

目前腳本生成不是單純把表單丟給模型，而是改成兩段 LLM：

  1. industry_research：依產業、人設、平台、目的推理受眾、痛點、信任障礙、常見情境、角色關係。
  2. generate_script：讀取 industryInsight、persona、CTA、禁語、學習資料與記憶，再產出正式腳本 JSON。
persona + params + learnedTexts + memories
        ↓
LLM stage 1: industry_research
        ↓
industryInsight
        ↓
LLM stage 2: generate_script
        ↓
factBoundary / audiencePsychology / sceneLogic / blocks / qualityCheck

二、fallback 現況與剛修掉的問題

原本的危險點

server 裡有一個 buildFallbackScript()，原本用途是提供 JSON shape 與本機 smoke test 的預設內容。但之前存在一個危險狀況：

如果 LLM 有回 JSON，但 blocks 是空的
normalizeScriptOutput() 會用 fallback.blocks 補上
前端看起來像真的產出了一份腳本

這會讓 fallback 偽裝成正式腳本，不能接受。

目前已修正

現在已改成：

如果 LLM 沒有回有效 blocks
server throw apiError('generate_script', 'invalid_script_output_missing_blocks')
前端顯示「API 錯誤，請聯繫官方」
不新增假草稿

也就是：fallback 不能再補出正式腳本 blocks。

三、目前仍可能不夠像 TG HERMES 的地方

問題 目前狀況 需要原始 Agent 協助
行業切換後劇情不夠不同 已新增 industry_research，餐飲會跑出外帶、排隊、飯糰；裝修會跑出報價單、另計、追加預算。 提供 TG 端如何依產業選擇角色、場景、衝突的規則。
真人句還不夠狠 現在 prompt 要求短句、反應、追問，但仍可能偏保守。 提供 TG 端常用口語節奏、吐槽強度、藏鏡人拆話的規則。
故事可能仍像「解釋服務」 已要求先模擬現場，但模型有時仍會回到說明型文案。 提供「現場模擬 → 真人句 → 故事骨架 → 正式 blocks」的更硬性判斷標準。
缺資料時的自由度 目前規則是：硬事實不能編，情境可以演，行業常識可以安全推理。 確認 TG 端對「安全行業常識」與「不可亂編事實」的邊界。

四、想請原始 TG Agent 回答的問題

  1. 當使用者只填產業、人設、受眾，但幾乎沒有學習資料時，HERMES 應該怎麼推導第一個可拍場景？
  2. 不同行業的「角色關係」應該怎麼選？例如餐飲、美業、裝修、教育、B2B、政治服務。
  3. 藏鏡人應該在什麼時候吐槽、追問、打斷？有沒有固定判斷規則？
  4. 「真人句」的檢查標準能不能更具體？例如幾個字以內、是否要有停頓、是否要有反應詞。
  5. 如何避免腳本變成公司介紹、產品說明、服務簡報？
  6. 如果資料不足，哪些地方可以用行業常識補，哪些地方一定要問使用者？
  7. 可否提供一份 TG 端腳本引擎的 JSON schema 或 pseudo-code？

六、目前我方需要確認的結論

現在正式路徑應該是 LLM 自動生成，不是 fallback 腳本。

但 buildFallbackScript() 這個函式仍存在於 server，未來最好改名成 buildScriptSchemaDefaults()，只保留欄位形狀與安全預設，不放完整腳本台詞，避免任何人誤用。

下一步建議：請原始 TG Agent 回傳劇作規則後，把 fallback 內容完全改成 schema-only，讓任何正式腳本都必須來自 LLM blocks。
